# TalentOS as a recruiting harness

The owner's framing, 2026-09-07: _"i want talentOS to be like the recruitment
openclaw. Figuratively not literally… rather than its own models it makes ai
models better at executing code."_

Read before writing this: the OpenClaw documentation and the agent-harness
write-ups, `src/lib/services/crew.ts`, `src/lib/ai/run.ts`, the task
definitions in `src/lib/ai/tasks/`, `fair-hiring.ts`, and D-008.

---

## 1. What a harness is

An agent is not a model. It is a model plus **memory, instructions, tools,
triggers, outputs, and a loop**. The finding that makes this worth chasing:
changing only the harness — the agent loop, the tool interface, workspace
management, the stopping policy — produces performance differences
comparable to or larger than moving to a neighbouring model tier.

Applied here: TalentOS should make any competent model good at recruiting.
Not by having a better model, which it will never have, but by being the
structure the model works inside.

## 2. Where TalentOS already is one

| Part            | State                                                                                                                                                                 |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Model           | **None of its own.** Provider-agnostic by construction (D-008): Anthropic, a Claude session, or mock. Right already, and by accident of the no-key constraint.        |
| Memory          | **Strong.** The canonical IR is a single interpretation the model consumes rather than re-derives. Records, tags-as-pages (D-039), the knowledge graph, HSAL beliefs. |
| Instructions    | **Strong.** A system prompt per task, the non-inference directive in every one, the coaching layer (D-047) that says why a move matters.                              |
| Tools           | **Present.** The open index (D-040), registries, declared-link adapters, link-out, document extraction, the query composer.                                           |
| Outputs         | **Strong.** A zod schema per task, validated at the boundary, with a fair-hiring scan and an audit row before anything persists.                                      |
| Loop            | **Present.** `crew`: a dependency-ordered queue running generate → critique → revise → done, each step through the same validation pipeline.                          |
| Stopping policy | **Present.** One revision, then done. Explicit rather than emergent.                                                                                                  |
| Workspace       | **Partial.** The session outbox is a workspace of a kind; there is no scratch space a model can use across steps.                                                     |
| **Triggers**    | **Missing.** Everything waits for a person to press something.                                                                                                        |

## 3. The gap, and what it is worth

**Triggers are the gap.** The daily briefing (D-047) already computes the
conditions — a stalled candidate, an unanswered intake question, a follow-up
past its date, a belief nobody has revisited (D-051). Nothing acts on any of
it. A harness whose loop only starts when a human starts it is a tool with a
loop in it, not an agent.

What a trigger may do here is bounded by a rule that predates this framing
and outranks it: **agents draft and analyse; they never decide, send, or
reject.** So a trigger queues work for review. It never contacts anybody,
never advances a stage, never rejects a candidate. That constraint is not a
limitation of the harness — it is the product's position, and a harness that
broke it would be a different product.

The second gap is **workspace**. A model working a search has no scratch
space that survives between steps; each task gets context assembled for it
and returns a typed payload. That is clean, and it is also why nothing can
carry a half-formed idea from one step to the next.

## 4. What follows from taking the framing seriously

1. **Triggers that queue, never act.** A condition in the records enqueues a
   crew job; the output lands as an editable draft with its provenance. The
   recruiter finds work done rather than a notification asking them to do it.
2. **The tool interface is the product surface.** If the harness is the
   value, then every capability should be callable by a model in the same
   shape a person calls it — the open index, the composer, the registries.
   Today several are UI-first with a service underneath.
3. **Stopping policy per task, not one global rule.** One revision is right
   for a draft and wrong for a search string that can be measured against
   yield.
4. **Say it in the product.** Nothing in TalentOS tells a reader it is a
   harness rather than an app with AI features, and the difference is the
   whole proposition.

## 5. What this framing does not license

It does not license autonomy. It does not license contacting anyone. It does
not license a model deciding about a person. Every guardrail in `LEGAL.md`
and `fair-hiring.ts` binds the harness exactly as it binds the app, and the
harness framing makes them more important rather than less: a loop that runs
without being asked is precisely where an unchecked rule does its damage.
